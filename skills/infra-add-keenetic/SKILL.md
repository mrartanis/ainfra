# Подключение Keenetic к Infra

Прочитай [процедуру подключения](../../docs/keenetic-inventory.md). Сборщик работает на `pi`; endpoints — внешний HTTPS адрес или KeenDNS через облако. Не заменяй эту схему обязательным VPN и не определяй режим подключения по суффиксу домена.

Infra хранит инвентарь. Административные credentials внешнего LLM-администратора остаются на машине его запуска. Для pi выдай отдельную учётку с тегами `readonly` и `http`; секрет и scoped token Infra хранятся только на pi. Разовый admin-пароль передавай через SSH stdin без argv, логов и временной копии на pi. Удали исходный файл в согласованный с владельцем момент после успешного подключения.

Для подготовки учётки используй [scripts/provision-user.py](scripts/provision-user.py). На KeeneticOS 5.1.6 работает `user.password.md5.hash`; плоское поле `password` не устанавливает пароль. Имя пользователя допускает `_`, но не `-`. Helper проверяет версию, статусы RCI внутри HTTP 200, теги и чтение через новую учётку. Не считай HTTP 200 подтверждением выполнения команды.

Не запускай helper на настройку по запросу только на диагностику: создание учётки и сохранение конфигурации — действия подключения устройства. При ошибке авторизации останови повторные попытки, выясни причину; серия неправильных входов может временно заблокировать источник. Не отключай readonly ради исправления опроса и не подставляй admin в постоянный config.

Зарегистрируй обычный `Node(kind=router)` с проверенными hostname, моделью, площадкой и public keys всех WG-интерфейсов. Проверь каталог, чтобы не создать дубликат. Не записывай IP облачного proxy как IP устройства и не размещай NAS/pi на роутере через `runs_on`. Если владелец назвал роутер входной точкой площадки, включи флажок в карточке или задай `labels.entry_point="true"`; тип `router` остаётся независимым. В одной площадке может быть несколько входных узлов. Туннель или default route эту роль не назначает.

Выдай отдельный `probe` token только на UUID роутера, привязанный к instance сборщика. Не переноси admin token Infra на pi. Добавь target с `type=keenetic` в `/etc/infra-probe/agent.json`, сохрани прежние targets и state/sequence. Устанавливай проверенную ARMv7 сборку в `/usr/local/bin/infra-probe`; обычный Linux-agent pi не заменяй.

Перед включением таймера выполни `check-config`, запуск service и проверку **применённого** отчёта через API. Ack `queued` означает только приём в inbox. У обоих timestamps (latest status и last-good section) должна быть свежая дата, а `os`, `network`, `wireguard` должны быть `ok/complete`; для устройства без WG успешный пустой WG snapshot допустим. Проверь очередь, права 0600 на секретах, включённый timer и повторный sequence. Ключи/пароли/Authorization не должны попадать в payload или вывод проверки.

После подключения проверь карточку, context и topology. Подтверждённые публичные ключи связывают туннели; endpoint IP или имя peer недостаточны. Отсутствие findings не означает CVE-покрытия Keenetic.
