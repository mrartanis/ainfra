# Площадки и gateway

Статус: отметки входных точек и маршрутизаторов на карте реализованы, 2026-10-22. Отдельная сущность Site ниже остаётся предложением. В текущем runtime площадки/хостеры представлены меткой `labels.provider` корневого узла, наследуемой через `runs_on`.

## Значение gateway

У площадки может быть ноль, одна или несколько входных точек (gateway), явно указанных владельцем. Входным узлом может быть сервер, гипервизор или маршрутизатор. Он помогает человеку и внешнему LLM-администратору понять путь доступа; сам инвентарь не устанавливает через него административные соединения.

Это роль узла в площадке. Наблюдаемый default route, VPN peer или существующая связь `uses_gateway` сами по себе не назначают gateway площадки. Один и тот же узел может одновременно быть гипервизором, gateway и объектом сбора инвентаря.

Начальное назначение со слов владельца:

| Площадка | Gateway |
|---|---|
| IBG | node0.c.ibgene.org (`node0`) |
| 1dedic / площадка bp2 | bp2 |
| belgrade | Keenetic `artanis-bg.keenetic.pro` |
| MSK-artanis-butovo / площадка pi | Keenetic `artanis.netcraze.pro`, a14d77cc-c48a-468f-8ce0-ea9a614bea08 |
| MDVOR | pve02.hintlab.com (`pve02`) |

## Отметки в текущем инвентаре

`Node.kind=router` обозначает маршрутизатор. Независимая ручная метка `Node.labels.entry_point="true"` обозначает входную точку площадки. Её можно включать и снимать флажком «Входная точка площадки» в редакторе узла. Она не наследуется VM/LXC, не вычисляется из типа, IP, `labels.role`, маршрутов или WireGuard. Несколько узлов в одной группе могут иметь эту метку одновременно.

Карта выделяет маршрутизаторы цветом, входные точки — рамкой и бейджем «Вход». В заголовке каждой площадки показано число её входных точек; при раскладке одноуровневые входные узлы идут первыми. Отметка видна в карточке, API, context и экспорте через существующие labels; изменения схемы БД или API не требуются. Старые формы редактирования, не передающие этот флажок, сохраняют отметку.

## Предлагаемый контракт отдельной Site

Ввести отдельную сущность `Site`:

```json
{
  "id": "SITE_UUID",
  "name": "belgrade",
  "provider": "",
  "location": "Belgrade",
  "entry_point_node_ids": ["KEENETIC_NODE_UUID", "ANOTHER_ENTRY_NODE_UUID"],
  "revision": 1
}
```

Обязательны UUID и имя. `provider`, `location` необязательны; `entry_point_node_ids` — список UUID без дубликатов, пустой список допустим. В `Node` добавить необязательный `site_id`. Каждая ссылка на входную точку — UUID существующего узла, не hostname/IP и не встроенная копия роутера. Секретов в Site нет.

Хостер и площадка становятся разными понятиями: у одного хостера может быть несколько площадок, а у домашней площадки хостер может быть неизвестен. Старый `labels.provider` остаётся совместимым на время перехода; автоматическое преобразование произвольных одинаковых строк в Site не выполняется без проверки владельца.

## Размещение и наследование

- Площадка назначается корневому хосту вручную. Его VM/LXC наследуют её по `runs_on`. Физические соседние узлы, например NAS и Keenetic, относятся к одной Site, но не размещаются друг на друге.
- `nas → runs_on → Keenetic` и `pi → runs_on → Keenetic` не создаются. Gateway не становится контейнером для остальных узлов.
- Узлы без Site и площадки без gateway допустимы. Если размещение неоднозначно или явная площадка ребёнка противоречит площадке хоста, это требует разрешения конфликта; произвольная площадка не выбирается.
- Назначение gateway не создаёт автоматические связи между всеми узлами, не меняет маршруты и не доказывает сетевую достижимость. Публичные адреса/сервисы и инструкции доступа описываются в самой карточке gateway без секретов.

## Поведение API, UI и context

Предлагаемые операции: `GET/POST /api/v1/sites`, `GET/PUT/DELETE /api/v1/sites/{id}`. Чтение доступно reader/editor/admin, изменение — только admin с revision/If-Match. Collector не может менять Site, `site_id` и gateway через observations.

Проверять существование и активное состояние каждой входной точки, принадлежность этих узлов площадке и все ссылки при изменении. Удаление используемой Site/gateway требует сначала явного снятия ссылок; иначе conflict. Self-loop на карте не нужен, если корневой хост одновременно является gateway своей площадки.

В UI отдельная Site получает карточку/редактирование с выбором нескольких входных узлов. Карта показывает gateway в группе площадки; размещение VM/LXC остаётся прежним. В node context и экспорт включаются эффективная Site и краткие карточки всех входных узлов, чтобы LLM-администратор видел доступные входы без обхода всего каталога. Внешний администратор выбирает способ подключения и получает свои credentials на собственной машине.

Реализацию стоит начать с Site/Node/API и проверок ссылок/наследования, затем добавить UI/context и перенести подтверждённые площадки. Опрос Keenetic с pi не зависит от появления Site: target привязывается к постоянному UUID роутера.
